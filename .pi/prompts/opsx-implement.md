---
description: "Implement an OpenSpec change with subagents, then sync, archive, and merge locally"
argument-hint: "[change-name]"
---

Deliver the OpenSpec change named in these arguments: $@. If none is given, infer the change only when unambiguous; otherwise list active changes and ask me to choose. Do not start implementation until the change is selected.

1. Use `using-git-worktrees` to detect existing isolation or create a feature worktree from the local checkout's base branch. Follow its safety and setup steps, but skip baseline tests: assume the starting branch is clean. Run the full suite before syncing and archiving. Record the worktree path, branch, base branch, and its starting commit for finishing; do not work on main. Before implementation, inspect the selected change's files in the starting checkout: a new worktree does not include uncommitted files. If the selected OpenSpec change directory is wholly untracked, move only that directory into the new worktree at the same relative path after worktree creation succeeds, and verify its contents arrived. Leave unrelated changes alone. If it contains tracked modifications or staged files, or the destination already exists, stop and ask how to transfer it safely rather than overwriting or discarding anything. If already in an isolated worktree with the change present, do not move it. Preserve all other pre-existing changes in the local checkout.
2. Use `openspec-apply-change` to read the selected change's status, apply instructions, and every returned context file. Treat approved OpenSpec artifacts as the planning authority; do not create a competing plan. Follow its blocked-state, scope, progress, and task-completion rules. Continue through every remaining approved task, not just a passing milestone.
3. Use `pi-subagents` to implement the tasks as `subagent-driven-development` would: the parent coordinates, a fresh bounded implementer works on each task (batch only small same-shape tasks), and a fresh independent reviewer checks both spec compliance and code quality after each task. Keep one writer at a time in the worktree; pass exact worktree paths, relevant requirements, edit boundaries, and validation instructions to each child. Set each subagent's model explicitly to the parent session's current provider/model at launch, including implementers and reviewers. Have implementers use `test-driven-development` (observe red, implement minimally, verify green), self-review, and report tests. Task commits in the worktree are intermediate; do not use the `commit-message` skill for them. Resolve review findings with the Superpowers fix/re-review loop before moving on. The parent retains decisions and updates OpenSpec task checkboxes only after verified completion. Children must not spawn subagents, sync specs, archive, or merge. If subagent tooling is unavailable or fails, stop and report it rather than silently switching execution modes.
4. Verify each task and address review blockers before moving on. Once all implementation tasks are complete, obtain a fresh whole-branch implementation review, address blockers, and run `cargo test --all --workspace -- --test-threads=1` with a tool timeout of at least 5,400 seconds; a timeout is not a pass. If implementation changes after this run, rerun the suite before integration. Stop for OpenSpec ambiguities, unapproved scope, failed tests, or other genuine blockers rather than guessing or silently dropping requirements.
5. Only after that gate passes, use `openspec-sync-specs` in the parent session, validate the synced main specs, then use `openspec-archive-change` in the parent session. When archiving, verify the delta specs are already synced; do not archive without syncing. Commit all task, spec, and archive changes on the feature branch so the worktree is clean before integration; do not use the `commit-message` skill for these intermediate commits. Do not archive while a sync is running. Inspect the final diff and apply `verification-before-completion`. Syncing and archiving do not require another full test run.
6. Use `finishing-a-development-branch` with my requested **squash-merge** variant of its local-merge option, subject to any confirmation that skill requires. Confirm the base branch if uncertain and check that the **main local checkout** has no changes that would be overwritten; do not pull or push to a remote without asking. In the main local checkout, squash-merge the feature branch so the combined changes are staged. Use the `commit-message` skill once on that staged squash diff to draft the final message, then commit the squash separately (the skill itself does not commit). If the base branch has not advanced since worktree creation, the squash applies without conflicts or other changes, and no implementation changed since the full-suite run, reuse that test result instead of running the suite again. Otherwise run the full suite on the merged result before cleanup. Remove the worktree only after a successful commit and applicable green tests; a squash commit does not make the feature branch an ancestor, so do not force-delete the branch just to make cleanup pass. If merge, verification, or cleanup fails, preserve the worktree and branch and report the blocker; never force-remove uncommitted files.

Report task progress, verification results, synced specs, archive path, merge result, and worktree cleanup status. Keep going until delivery is complete or a decision/blocker actually requires me.
