# Commit changes — Git guidance

For commit requests, call `commit_changes` with `action: "start"` (or continue after the user runs `/commit-changes`). To target a registered worktree, pass `worktree: "path"`; if the exposed API schema omits that field, pass `proposal: {"worktree": "path"}` **on start only**. Verify the returned inventory names the intended checkout before proposing a group; stop immediately if it does not. The Pi extension owns Git effects and human menus; this skill supplies Git judgment, not a route around its gates. Do not run Git mutations yourself. In an active run, use `commit_changes` for read-only inventory and all decisions/effects; `read` is available for inspecting individual files.

## Commit judgment

- Inventory `git status --short --branch`, full tracked and staged diffs, untracked files, relevant source/history, and repository checks. Explain the intent and membership of each coherent file/hunk group. Separate unrelated changes; do not mix mechanical cleanup with behavioral changes merely because they touch the same file. If a patch cannot safely be split, say so rather than guessing.
- Review untracked files individually. Exclude ad-hoc notes, scratch/temporary files, generated artifacts, secrets, and files unrelated to a group unless required for that group's behavior. Name exclusions and uncertainties explicitly; never use `git add -A` or globbing that sweeps them in.
- Respect pre-existing staged content. Inventory and propose it as one intact first group; if it mixes unrelated work, stop for direction. Never silently unstage, overwrite, discard, or mix it with another group. Skipping an already-staged group leaves the index untouched.
- First submit `propose` with `{"groups":[{"source":"working|staged","reason":"theme","changes":[{"path":"path","hunks":["optional inventory hunk IDs"]}]}],"excluded":["path: reason"]}`. Use exact file/hunk membership and short rationales, plus explicit exclusions; do not write patch text for the first approval. The extension generates stageable patches from approved membership and checks the staged content internally. If part of a file cannot be safely separated, exclude it and say why.
- After `stage`, draft from the **entire** staged diff. Follow **Commit message conventions** in `../commit-message/SKILL.md`; its draft-only stopping rule applies only to standalone message requests. Send the exact message with `present_message`, then call `decide_message` in a subsequent turn so it is printed in the conversation before the menu. For approval call `commit`; for revisions present the new message and ask again. Do not print the staged diff yourself or run tests for this procedure.
- For a hook failure, choose Fix in the human menu before editing, fix only issues within the approved group's meaning, and supply only the repair hunk as a unified `patch` to `repair` against the staged index. Leave excluded hunks unstaged. The extension rechecks the changed staged diff and requires a freshly presented message and approval. If a partial-file repair cannot be isolated, stop. After committed groups in the main checkout, call `review_push`. After committed groups in a linked worktree, offer `local_merge` into the main checkout instead; do not offer a push from that worktree. If a push is rejected, use `fetch_resolve` only after the human approves it. Resolve only named merge conflicts, then use `review_merge` and `commit_merge` for a separate approval. Never bypass hooks, rebase, force-push, choose a new upstream, or discard unrelated work. If reconciliation would affect unrelated work, stop and ask.

For a requested **local** merge, use `commit_changes(action="local_merge", proposal={"worktree":"registered source path"})` to merge into the main checkout. The source and target tracked files must be clean. A fast-forward permits unrelated untracked target files but rejects paths overlapping the incoming changes; a non-fast-forward still requires both worktrees entirely clean. Call `perform_local_merge`. For a fast-forward, there is no merge commit or review: verify the result, then call `remove_worktree` for separate cleanup approval. For a non-fast-forward, call `review_merge` and `commit_merge` in order; inspect the entire staged merge and printed message before its separate commit menu. No push occurs. Cleanup removes only the clean merged source worktree and retains its branch. If a step fails, stop and report the Git state; never abort or force-remove on your own.

Only choices made in the extension's human menus authorize Git actions. One approval never authorizes a different group, changed message, or later merge resolution.
