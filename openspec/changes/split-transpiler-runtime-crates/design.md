# Design

## Context

See proposal.md and specs/project-build/spec.md and specs/process-runtime/spec.md. The root package currently exports both compiler and runtime; `src/project.rs` generates `.blkit/Cargo.toml` with `blkit`, `tokio`, and `axum` for every target. `src/runtime/mod.rs` imports both Turso and PostgreSQL, and `src/compiled_graph.rs` uses public runtime aliases. `build.rs` compiles `examples/graph.bl` for repository binaries. `DistributedControl` currently receives full compiled definitions: it validates typed start input, creates the initial checkpoint, persists retry/deadline policy, and reconciles expired claims. Workers already register namespace/version/process capabilities and heartbeats in PostgreSQL, but claim selection does not currently require a fresh heartbeat. The local `Engine::start` currently validates input, initializes a checkpoint, persists the instance, and immediately spawns `run_named` as an async task with a semaphore bound; it does not poll a local durable queue. The active `add-temporal-expressions` change may add shared helper APIs.

## Goals / Non-Goals

**Goals:** Preserve the `blkit` CLI and existing `crate`, `worker`, and local `server` targets; add explicit source-free remote API-only, local/remote combined API+worker, split remote API+worker, and remote worker-only targets; make a local in-process worker claim persisted work; let remote API-only binaries omit compiled definitions and worker execution code; exclude unrelated normal dependencies from each independently built output while retaining durable process semantics.

**Non-Goals:** Separate published API/worker crates, change `.bl` grammar, independently version core/transpiler, promise a fixed build-time reduction, remove the local server, or guarantee that a worker remains available after request admission.

## Decisions

1. **Two workspace packages, one-way dependency.** `blkit-transpiler` owns parser, semantics, codegen, project generation, `build.rs` for repository example binaries, and the binary still named `blkit`. It depends on `blkit-core` for shared compiler/generated helpers and policy types. Core owns graph/runtime and optional service/storage modules and never depends on the transpiler (including build dependencies). Coordinate package versions and emit an exact `blkit-core` version, using the actual core package directory as a local path when present. Continue validating `blkit.toml`'s `blkit` field against the CLI. Alternative: a feature-gated single package still exposes compiler/runtime dependencies and APIs under one published package.

2. **Additive capabilities, not mutually exclusive targets.** Keep minimal core defaults with graph definitions, evaluation aliases, and shared generated-code helpers. Expose `api-server` for HTTP, `worker` for execution using either storage backend, `local-persistence` for the local store, `remote-persistence` for PostgreSQL admission/claims, and `logging` for configured operational logging; gate their heavyweight dependencies as optional. The local combined target selects `api-server` + `worker` + `local-persistence` + `logging`; remote combined selects `api-server` + `worker` + `remote-persistence` + `logging`; remote API-only selects `api-server` + `remote-persistence` + `logging`; remote worker-only selects `worker` + `remote-persistence` + `logging`. `crate` selects none. The legacy `server` and `worker` targets map to local combined and remote worker-only. Both persistence features may be enabled together; Cargo feature unification is additive, so do not reject the combination. `worker` supplies the execution role with backend-specific queue adapters, not a requirement that local execution use the existing PostgreSQL worker implementation. HTTP routes and base graph aliases must compile with only their concrete backend features. Alternative: feature names tied to server deployment conflate HTTP with persistence and fail when features unify.

3. **One project target selects an output layout.** Keep the single `build_target` string and support `crate`, `api-only`, `api-worker`, `api-worker-split`, `worker-only`; retain `server` and `worker` as compatibility aliases for local `api-worker` and `worker-only`. For `api-worker` require an explicit `persistence = "local" | "remote"` field in `[project]`; the other new targets have fixed backends and do not need that field. `api-only` emits an independent PostgreSQL-backed HTTP project and accepts a project with zero `.bl` files: it does not emit a compiled process library, and admits any identity advertised by a live worker connected to the same store. When sources are present, still validate them without linking their definitions into the API. `api-worker` emits a single API+worker executable with the selected backend. `api-worker-split` emits separately buildable remote API and worker packages under `.blkit`, with only the worker package depending on the generated definitions library; preserve the root generated library/manifest path for Rust consumers and use a small sibling member package for split API. Document building each split package independently to avoid Cargo unifying features across a workspace-wide build. Alternative: two `src/bin/*` targets in one package would compile the union of package-level core features and defeat smaller builds.

4. **Admission via PostgreSQL, initialization via worker.** For distributed starts, query worker capabilities joined to workers in PostgreSQL for the exact namespace/version/process, a non-draining registration, and a sufficiently fresh heartbeat based on database time. Use the same transaction to check admission and insert a pending instance with raw syntactically valid JSON and no checkpoint; if no matching live worker, report unavailability and create nothing. This check is a snapshot, not a reservation: if a worker disappears after acceptance, the instance stays queued for another matching worker. On claim, the worker validates typed port input and constructs/checkpoints the graph before executing any task; invalid input atomically becomes terminal failed with an actionable reason, not a retryable attempt. Malformed HTTP JSON remains an immediate client error. The local server keeps immediate validation. Alternative: send full graph definitions to the distributed API as today, which makes its binary compile and link the worker logic.

5. **Persist policy without executable graph in the API.** Registration publishes the minimum process identity and policy metadata needed for queue-origin deadlines and retries (not compiled closures). Reject inconsistent metadata advertised for the same identity/version so API admission does not pick an arbitrary policy. Persist the selected policy and queued-at deadline on the instance at admission; first-claim-origin timing still begins on first claim. Worker claims initialize checkpoints, and expired-claim/control reconciliation reads persisted policy rather than a local graph registry. Cancellation and deadline checks must also fence a worker during initialization, and status/error records must remain durable. Existing queued instances with checkpoints remain readable during migration. Alternative: wait until worker claim to learn all policies; that loses queue-origin deadline enforcement when no worker claims an instance.

6. **Local API queues, local worker polls.** Keep the existing immediate typed-input validation and checkpoint initialization on local admission, then persist pending work without spawning `run_named` from the request path. An in-process worker loop polls and claims eligible pending instances from the existing local store; use its durable instance rows as the queue, not a second table/service. Bound execution by the existing task semaphore, exclude cancelled/expired work at claim, and wake/poll on startup so persisted pending instances run after a crash. On restart, preserve current recovery semantics for interrupted running work, completed checkpoints, retries, waits, and deadlines; the queue poller does not treat an unclaimed pending instance as a failed attempt. Alternative: rename existing `tokio::spawn` work as a worker without a durable polling boundary; this would not satisfy the local-queue requirement.

7. **Generated imports and migration.** Switch emitted Rust/templates to `blkit_core::` and reserve `blkit-core` as an internal dependency. Generate only the direct dependencies used by each generated package. Retain direct `SOURCE.bl OUTPUT.rs` without project manifest, document required core/data-type deps, and adjust test fixture root paths and example binaries for the workspace. Regenerate/resolve Cargo.lock after the renamed dependency, and compile the API and worker separately when measuring dependency isolation.

## Risks / Trade-offs

- [A live worker can vanish after admission] → Keep a durable pending instance; liveness is an admission check, not a delivery guarantee. Test stale/draining workers, version mismatches, and post-admission exit.
- [Input-validation timing is externally visible] → Document remote 202 acceptance followed by terminal failed status; keep immediate malformed-JSON rejection and local-server validation. Test that invalid remote starts never execute tasks or retry.
- [Local queue changes restart/claim timing] → Use existing instance persistence, claim only pending eligible work, and test restart, cancellation before claim, retries, waits, and concurrency instead of treating startup polling as a fresh execution attempt.
- [Policy/version skew across worker registrations] → Store immutable per-identity policy metadata for a version or reject conflicting registrations; persist chosen policy at admission and test queue deadlines before claim.
- [Feature unification masks dependency isolation] → Check normal dependency trees and builds per selected generated package rather than a combined workspace build; separately exercise simultaneous `api-server`+`worker` and both persistence features.
- [Rust import break, build-script paths, temporal overlap] → Update generated/manual consumers, move example build script only to transpiler, and reconcile active temporal helper/codegen work before moving source files.

## Migration Plan

Coordinate the two crate releases. After upgrading the CLI, regenerate `.blkit/` sources/manifests, resolve the lockfile (explicit `blkit update` when required), and build new outputs. Direct Rust users replace runtime `blkit` imports/dependencies with `blkit-core`; compiler-library consumers use `blkit-transpiler`. A source-free API-only deployment needs worker binaries from another project using the same PostgreSQL store; deploy workers advertising their exact process/version before sending requests to definition-free distributed API binaries. Legacy `server` projects keep their config but switch to in-process local queue polling after regeneration. Existing checkpointed instances remain recoverable; new pending instances without checkpoints are initialized on worker claim. Roll back by regenerating and rebuilding with the previous CLI/core pair and their matching lockfile; do not mix old distributed APIs that require linked graph definitions with the new API-only output.
