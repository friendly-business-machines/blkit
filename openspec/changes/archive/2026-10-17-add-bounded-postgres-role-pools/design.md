# Design

## Context

See `proposal.md` and `specs/distributed-execution/spec.md`. `PostgresStore` currently wraps one `tokio_postgres::Client` in `Arc<Mutex<_>>`; all of its roughly two dozen query sites acquire that mutex, and several hold it for the entire transaction. A generated remote combined binary already constructs separate API/reconciler and worker stores, but each store has one client. `claim` locks the worker row before instance rows, so drain on another connection waits for an in-flight claim. Generated API-only, worker-only, combined remote, and split remote role binaries need the same connection-budget behavior; local persistence and library-only build targets do not.

## Goals / Non-Goals

**Goals:** Remove one-client-per-role serialization when PostgreSQL can handle concurrent work; keep sessions per process bounded and independently budgeted by role. Retain transaction and claim fencing, startup checks, positional CLI compatibility, and usable error reporting. Select and report a conservative default using measured API-only, worker-only, and combined workloads.

**Non-Goals:** Auto-size from CPU count, change the PostgreSQL schema or query/fencing semantics, promise throughput gains on every PostgreSQL deployment, introduce a pool for local persistence, or add knobs beyond the two role limits.

## Decisions

1. **Use `deadpool-postgres` only with `remote-persistence`.** Add its compatible 0.14.x release alongside the existing `tokio-postgres` 0.7 dependency (the published 0.14.2 manifest requires `tokio-postgres ^0.7.14`). Replace `Arc<Mutex<Client>>` with a clonable bounded pool. Parse the existing URL using `tokio_postgres::Config`, construct a `deadpool_postgres::Manager` with the current `NoTls` behavior, and expose `PostgresStore::connect_with_pool_size(url, max)` while keeping `connect(url)` as the four-connection default. Validate `max > 0` before pool construction; initialize the database using one checked-out connection during `connect`, so unreachable databases/schema errors still prevent startup. The pool may open additional sessions only as needed. Alternatives: a homegrown semaphore/client vector adds reconnect/health/transaction ownership code; `bb8-postgres` is viable but offers no advantage needed here. No unrelated prepared-statement cache/config surface.

2. **Checkout per operation, not per store lifetime.** Acquire a connection at each existing SQL call site; for multi-statement transactions keep the *same* checked-out connection through commit or rollback before releasing it. Preserve the current claim worker-row-first lock order, `FOR UPDATE SKIP LOCKED`, generation predicates, and transaction commit boundaries; do not hold a connection while executing task bodies. Keep existing `String` errors and include operation context for checkout failures without logging URLs, passwords, or payloads. Set finite pool wait, create, and recycle timeouts (initially 1s wait, 2s create, 1s recycle; check under load and lease tests); never treat a timeout as a committed write. Prefer the pool's normal fast recycle check to avoid an extra round trip on each operation; propagate a stale connection error and let the pool replace it rather than adding application-level write retries. Alternative: one long-lived checkout recreates today's bottleneck; pinging on every checkout adds SQL to the hot path.

3. **Expose two role limits without changing CLI syntax.** Generated remote entrypoints read `BLKIT_API_DB_POOL_MAX` for API/reconciler and `BLKIT_WORKER_DB_POOL_MAX` for worker, default four each, accept only positive `usize` values, and report the setting name on invalid input. Only parse settings for active roles. Remote combined retains its two independent stores with separate budgets; split binaries each read only their own role's setting. Keep `MAX_TASKS` independent of connections. Document that worst-case server sessions are the sum of role limits across all running processes, plus observers/admin clients, subject to PostgreSQL/proxy limits. Local targets ignore both variables. Existing direct callers of `connect(url)` get a bounded four-client store; library callers may explicitly request one or more connections using the new constructor. Alternative: one shared pool in combined mode risks cross-role starvation; CPU-based sizing ignores database limits.

4. **Measure and test before claiming benefit.** Extend the existing explicitly opted-in disposable-database `postgres_contention` harness (and its documentation) with a worker-only workload and role-size sweep (1, 4, 8, 16, bounded by the disposable server's connection budget); do not change data sets between compared sizes. Record repeated throughput, API/request and worker/persistence p50/p95 latency, pool acquisition wait, database execution time, actual and peak PostgreSQL sessions, environment and commands. The old 23-site mutex instrumentation applies only to the baseline source; replace it with a comparable scoped checkout-wait measurement in the diagnostic harness and label incomparable windows/observer overhead rather than claiming an exact before/after mutex percentile. Record results and rationale for the four-connection default in this change's `measurement.md`. The measured API-side gains at eight connections do not change the chosen conservative default: the operator chose four to limit deployment-wide PostgreSQL sessions and will tune per-role limits through later stress testing. Document eight as an optional, capacity-budgeted setting rather than a universal recommendation. Preserve the existing 72/72/0 combined correctness assertion and test generated binaries separately. The API harness uses in-process router requests, so report that limitation; a larger node and PostgreSQL server may show different results.

## Risks / Trade-offs

- [More client sessions or overlarge operator limits exhaust PostgreSQL/proxy connections] → Open lazily, enforce per-role maxima, document summed deployment budgets and verify server-side session counts; fail visibly when sessions cannot be created.
- [Pool saturation or backend stalls delay heartbeat and lease renewal] → Bound checkout waits, exercise active-claim renewal and error/drain behavior under contention, and preserve generation fencing. A bound cannot guarantee lease survival through a PostgreSQL outage; document that risk.
- [Transactions or schema setup accidentally split across connections] → Keep one checkout until transaction end, initialize schema once per store, and run multi-connection PostgreSQL claim/drain, fencing, rollback and generated-role tests.
- [Failed/recycled connection is returned after a broken operation] → Let the manager discard/reconnect it, surface the original failure, and test recovery without automatically retrying non-idempotent writes.
- [Benchmarks induce bias or produce no gain] → Run repeated, same-workload comparisons with explicit observer and instrumentation limits; report negative results and no universal scaling guarantee.

## Migration Plan

No database migration. Updating `blkit-core` and regenerating/rebuilding remote binaries enables the four-per-role default; operators of connection-limited installations may set the relevant role environment variable to `1` before rollout to retain their prior session budget, then raise it after measuring available PostgreSQL capacity. Existing CLI arguments and `PostgresStore::connect` calls continue to compile. Roll back by using the prior core/generated binary; durable queue/lease data remains compatible.
