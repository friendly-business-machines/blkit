# Design

## Context

See `proposal.md` and `specs/business-language-tables/spec.md`. The expression pipeline is `crates/blkit-transpiler/src/expr.rs` (chumsky AST/parser), `semantic/types.rs` plus `semantic/constraints.rs` (type relations and name resolution), then `codegen/mod.rs` and `codegen/decision.rs` (generated Rust). Collection and dictionary helpers live in `crates/blkit-core/src/list_ops.rs` and `dictionary.rs`. `decision_table` is an unrelated decision-node construct. Current bracket syntax is single-argument list/dictionary indexing; `=` is rejected as equality and general-purpose `null` is not a value. Source-authored typing is explicit at ports; Table ports now require a declared named row shape, while table constructors infer columns and non-null types inside `.bl`.

## Goals / Non-Goals

**Goals:** Give table expressions one unambiguous parse/type/codegen path, maintain schema/order on empty results, report invalid shapes and runtime comparisons as errors, and preserve existing list/dictionary semantics.

**Non-Goals:** Table column-reference syntax for non-identifier column names, an authored `null` literal or authored null list elements, an independent query planner, SQL or database-backed execution, or changes to authored `decision_table` nodes.

## Decisions

1. **Distinct value and declared row-shaped ports.** Keep a dedicated, immutable table value in `blkit-core` with ordered column names, non-null per-column cell types and ordered rows; a nullable column may also contain null cells. Inside `.bl`, table constructors infer column names and non-null types from statically known headers and values, including typed/literal dictionary rows and empty named columns whose type comes from context; untyped dynamic dictionary keys cannot justify unchecked column references. Every typed table input/output port instead requires `Table<Row>` where `Row` names a declared dictionary schema; bare `Table` ports fail validation. A named schema such as `Order = {id: Number, price: Number?};` requires both fields; `?` permits a null value without changing `Number` as the type of non-null cells. The same field rule applies to an ordinary `Order` dictionary. Nullable `T?` may also appear where a nullable expression, projection or port result must be declared; it does not introduce a source-authored `null` literal. The declaration's field order defines table column order at typed boundaries. Check input shape and null permission as soon as supplied; reject incompatible typed outputs, missing columns, and invalid uses of nullable values during `.bl` transpilation whenever type/shape is statically determined. Use existing value/serialization infrastructure for cells without losing decimal precision or temporal semantics; never represent Table as `Vec<Dictionary>` at typed boundaries. `Value` may contain tables, but an untyped dynamic `Value` is not a source of statically checked table column references. Continue using `{columns: [...], rows: [{...}, ...]}` as JSON for typed `Table<Row>` ports; validate both fields and field types on standalone and project entry. Alternative: keep bare `Table` ports and cast cells when used; rejected because source references to unknown columns and values would fail only during evaluation.

2. **Separate table AST forms and scoped resolution.** Parse table selectors (including empty first slot, ranges, and column lists), method syntax, unquoted column references, `source -> destination`, assignment outputs, sort-key constructors, and `.groupBy(...).agg(...)` into distinguishable AST forms, not ordinary `Expr::Name`, dictionary indexing, or global function calls with unresolved names. Make `var(name)` a syntactically restricted outer lookup in table row/group expressions and reject unknown bare identifiers there even if an outer input exists. Keep `t` as a normal operand. Do not globally treat `=` as equality: only validated table comparison (or row-dictionary comparison within table iteration), aggregate/withColumn assignment, and existing named arguments use it. Type-directed dispatch keeps list `union` deduplicating and table `union` concatenating. Alternative: reusing generic call AST and looking up columns as ambient names; rejected because shadowing, missing-column diagnostics, and `=`/named-argument distinctions would be ambiguous.

3. **Single evaluation and checked relational helpers.** Implement row selector expansion, schema validation, stable sort, union, joins, and grouping in `blkit-core` helpers called from generated expressions; evaluate each operand/key/expression once and propagate fallible operations through the existing generated `Result` paths. Preserve column order independently of canonical-sorted `colNames`. Joins and `union(..., "all")` can introduce null cells and mark affected columns nullable; table projections/conversions preserve nulls, whereas authored `null` and `[null]` remain errors. A nullable input field can contain null only when its declared field permits it. Arithmetic involving null propagates null; comparisons and Boolean connectives use three-valued logic (including `not unknown = unknown`, `false and unknown = false`, and `true or unknown = true`). Table predicates retain only true rows (false and unknown are excluded). `sum` and `mean` ignore null elements, returning zero and null respectively when there are no non-null numbers, including an empty numeric list. `coalesce(value, fallback)` evaluates a fallback of the same non-null type only when the value is null, yielding a non-null result. Do not emit operations that implicitly treat nullable values as non-null; a nullable result requires an accepting type or an explicit fallback. For joins, use equal-key pair iteration and track unmatched rows (not a hash index initially, because structural value equality and fallible temporal comparisons must match existing `.bl` semantics). Bound Cartesian output and range expansion with checked arithmetic and explicit resource errors. Alternative: generated inline loops for every method; rejected to avoid repeating schema checks and error handling.

4. **Keep contextual typing sound.** Feed table-specific AST through both `infer_with` and `constraints::expression_branches`, including explicit row/group scopes, nullable values and aggregate result types; extend expression walkers for dependency detection, binding, and fallibility. Track statically determinable column names, non-null types and null permission through constructors, named `Table<Row>` ports, context/decision bindings and resolvable aliases; require an expected declared row shape or reject table column operations when a dynamic source supplies no statically determinable shape. An unknown column or invalid operand type fails during `.bl` transpilation, before Rust emission. Actual input JSON still requires validation when it arrives, before expression evaluation; data-dependent failures (such as invalid indices or division by zero) remain evaluation errors. A bound Table port uses its named row schema rather than an untyped dictionary guess. Dictionary/list equality remains `==` outside table-specific `=` contexts; null in structural table equality remains a cell value, while ordinary nullable comparisons follow the unknown/true-only-filter rules above. Alternative: defer column and cell checks to evaluation; rejected because it cannot meet the transpilation-time guarantee for `.bl` type and shape mistakes.

## Risks / Trade-offs

- [Requiring named `Table<Row>` ports breaks bare `Table` callers and existing docs] → Reject bare table ports with actionable diagnostics, update all examples and regenerate generated applications; tables constructed locally still infer their schema.
- [Nullable fields and nullable aggregate results affect existing named dictionaries and `mean([])`] → Require explicit `?` for null-accepting declarations, type-check nullable projections and fallbacks, and add regression tests for non-null dictionary/list operations.
- [General cell values may serialize differently from Rust `Number` and temporal values] → Reuse existing conversion functions and test JSON round trips, decimals, dates, and nested values in generated standalone and project outputs.
- [Broad parser extensions can change old list/dictionary/decision-table expressions] → Add regression tests for single-argument brackets, `==` versus `=`, named arguments, sequences, list union, and decision-table unary tests.
- [Join/range/cartesian growth and fallible comparisons can exhaust resources] → Check arithmetic and output sizes before allocation; use existing list sort/comparison rules where applicable; report errors, never truncate or panic.

## Migration Plan

No persisted schema migration. Existing `.bl` programs without tables retain their list/dictionary and decision-table behavior except the deliberate `mean([])` result change. Previously introduced bare-`Table` ports must be changed to `Table<Row>` and regenerated; nullable fields use `T?` without making absent keys optional. Rollback means reverting this language/runtime feature and recompiling affected generated applications; do not silently reinterpret stored Table JSON as a list.
