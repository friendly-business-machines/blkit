# Design

## Context

See [proposal.md](proposal.md) and [specs/business-language/spec.md](specs/business-language/spec.md). Expression parsing lives in `crates/blkit-transpiler/src/expr.rs`, typing in `semantic/types.rs`, and generated Rust in `codegen/mod.rs`; shared numeric/string/temporal helpers live in `crates/blkit-core`. `List<T>` already exists, while brackets currently mean a dictionary string-key lookup and `for`/`every` have one binding. Numeric aggregates return a scalar `Number`; `mode`'s signature and tie behavior therefore change. Tests in `crates/blkit-transpiler/tests/language.rs` and `generated.rs` exercise typing and compiled behavior. Range brackets (`[a..b]`), dictionary colons, string `indexOf`/`reverse`, and calendar/string/dictionary `isEmpty` must keep their current meaning.

## Goals / Non-Goals

**Goals:** One coherent typed expression pipeline for all existing decision/task/process contexts; reuse current decimal/temporal comparisons, error propagation, and generated-crate dependencies; keep operations immutable.

**Non-Goals:** Nullable or heterogeneous list literals, generic user-defined higher-order functions beyond the required inline match predicate, arbitrary comparator functions, or changing persisted process formats. The mixed-level `flatten([[1,2],[[3]],4])` and list-of-scalars insertion of a nested list from the raw examples are replaced by well-typed nested-list cases; they cannot be accepted under the single-type-list decision.

## Decisions

1. **Extend the existing expression AST and parser with distinct list constructs.** Resolve a bracket suffix as a numeric list index or Boolean list filter by the base and key types; retain dictionary string-key access. Add an explicit filter-only `.item` expression referring to the current list element, `some` and multiple ordered binding clauses to iteration, and a typed inline predicate form for `remove`/`listReplace`. Reserve `function` as the predicate introducer rather than permitting a knowledge model with that name; within the designated predicate argument, parse `function(i)` followed by a body (including unary and list-literal starts) as a predicate and reject a missing body. Reject leading `.item` outside bracket filter predicates; treat plain `item` as an ordinary name in decision nodes, context entries, inputs and iteration bindings. Dependency discovery shall recognize the explicit filter reference without hiding real dependencies in numeric positions or outer names. Keep ordinary field access such as `order.item` distinct from leading `.item`. Parse `start:end` only in expression position without absorbing dictionary entry separators; parse `mod` at multiplication precedence and delegate to existing checked `modulo` semantics. Reuse `Expr::Field` for typed list-of-dictionary projection and preserve scalar dictionary field access. Disambiguate literals from existing range syntax before emission. **Alternative:** interpreting all square brackets as generic dynamic lookup loses static validation and breaks dictionaries/ranges.

2. **Type-check every list operation and overload before generation.** Preserve `List<T>` and contextual inference for `[]`; reject incompatible/null elements, including accidentally mixed list depths. Distinguish numeric positions from Boolean filters and String dictionary keys; derive projection output from the field type, rejecting nonuniform or missing named fields. Keep `Value`-typed dynamic dictionary operations checked at runtime rather than treating a dynamic value as a typed homogeneous list without checks. Dispatch existing names (`indexOf`, `reverse`, `isEmpty`, `count`, `min`, `max`, `stringJoin`) on argument types; validate arity, element type, optional parameters and return types so a `mode` call now has `List<T>`. Maintain existing string/range/calendar semantics. **Alternative:** a single runtime-tagged list API would defer ordinary type mistakes and add conversions to generated Rust.

2a. **Infer empty iteration sources through shared, compositional typing.** The existing forward-only `infer_with` cannot derive a used binding's type from its body without either losing nested constraints or guessing at overloads. Make expression validation and reverse inference use the same typing rules for operands, results, calls, fields, generic collections, and overload alternatives; propagate expected result types inward and constraints on a binding outward, including through subsequent iteration sources. Represent unresolved types symbolically, reject recursive/incompatible solutions, and accept an empty-source binding only when its concrete type is uniquely determined across valid language types. A finite list of sampled types cannot prove uniqueness: an open `List<T>` or `Dictionary<T>` family counts as another possibility until constrained, and `x.active` alone cannot prefer a named record over `Dictionary<T>`. Report ambiguity for a used binding with multiple or unconstrained valid types; retain the existing non-observable type witness when an empty source's binding is unused, so `for x in [] return 1` still works. Validate the resolved type through the same rules and pass it into code-generation specialization rather than inferring it a second way. Preserve current nonempty iteration and string, number, dictionary, range, and temporal overload behavior, including the literal-zero duration subtraction rule. Add new overloads to this shared relation instead of maintaining a separate hint collector. **Alternative:** a local reverse-hint helper is smaller but incorrectly types `0 - x` and misses constraints in `x * 2 > 0`; enumerating a finite set of candidate types can falsely declare a unique result.

**Incremental migration of decision 2a:** Start with symbolic type terms, structural unification with an occurs check, and overload alternatives that retain unresolved generic families rather than enumerating candidate concrete types. Migrate the existing `infer_with` cases in bounded families—operators, fixed signatures and knowledge calls, temporal/calendar calls, dictionary/collection calls, and fields/iteration—so ordinary validation and reverse constraints delegate to the same rules as each family moves. Only after those rules are shared should empty-source binding resolution and code-generation specialization consume them. Intermediate slices may leave the already observed empty-iteration tests intentionally RED; their unit tests and previously passing behavior must be verified, and the final integration slice must make every language/generated test GREEN. Do not add a second independent inverse ruleset or treat the finite set of declared types as exhaustive.

3. **Keep runtime algorithms in the smallest reusable layer.** Emit direct Rust `Vec`/iterator operations where straightforward; share checked one-based index conversion, slicing, sequence bounds, stable deduplication/sorting, and zip formatting in `blkit-core` where repeated across generated sites. Compare numbers with `Number` ordering, strings by code point, and time/duration types using the existing same-kind comparison rules (including naive/zoned errors); use stable sorting with checked comparisons instead of silently imposing an arbitrary Rust ordering. For duration `sum`/`mean`/`median`, reuse checked temporal arithmetic and Number division; keep numeric `product`/`stddev` logic. Handle modes as an ordered collection of tied values, numeric ties sorted ascending and unordered-type ties in first-occurrence order. Fail on zero sequence steps, invalid indices, incompatible zones/types, arithmetic overflow and excessive allocation; pass failures through existing fallible generated-expression paths rather than panic. **Alternative:** generating every algorithm inline multiplies code and makes error handling inconsistent.

4. **Use the existing test layers as acceptance proof.** Add parser/type tests for syntax, overloads, invalid shapes/types and preserved range/dictionary/string behavior. Add generated-code tests exercising every list function family in a decision task and representative task/graph contexts, plus boundary cases for empty lists, negatives, decimal sequences, sorting, `mode`, and failed runtime operations. Keep example/documentation code type-correct and explicitly note the two user exceptions; don't treat the original heterogeneous and mixed-depth examples as valid programs. **Alternative:** unit tests of helpers alone cannot prove generated callers and semantics agree.

## Risks / Trade-offs

- [Existing scalar `mode` users fail type validation/build] → Document return-type migration; update affected tests/examples and require callers to select an element if they want one number.
- [Filter element names are confused with outer bindings or decision/context dependencies] → Use explicit filter-only `.item`, reject it elsewhere, and test Boolean-call/field filters alongside numeric positions and forward-declared records.
- [Shared constraint typing diverges from existing overload validation or admits an ambiguous binding] → Use one typing relation for ordinary validation and empty-source inference, reject unconstrained/open-generic solutions, and regress numeric, duration, dictionary, record, nested iteration and generated-code behavior before building later list overloads.
- [Parser ambiguity between list filters, dictionary lookups, ranges, and colons] → Add targeted syntax and negative tests, retain old precedence and old forms.
- [Dynamic dictionary projection or `Value` fields may fail at runtime] → Validate static schemas; propagate runtime missing-field/type errors instead of inventing nulls.
- [Sorting mixed temporal zone kinds and generating huge sequences can fail] → Use existing checked comparisons and checked size/arithmetic paths; verify errors in generated code.
- [OpenSpec source examples include invalid heterogeneous/mixed-depth lists] → Record the explicit homogeneous/no-null override in spec and tests rather than introducing implicit coercion.

## Migration Plan

Existing sources continue to work except scalar `mode` outputs/callers; migrate scalar modes to `List<T>` and select an element explicitly when desired. New filter examples must use `.item`; plain `item` remains available as a decision/context name and elsewhere. Regenerate generated crates and run compilation/tests; no stored data migration is required. Reverting the change and rebuilding restores prior behavior but programs using newly added list expressions will no longer compile.
