# Design

## Context

See `proposal.md`. `crates/blkit-core/src/server.rs` currently extracts `Json<Value>` for process starts. Local `Engine::start` validates typed input immediately, whereas `DistributedControl::start` admits syntactically valid JSON for a worker to validate. Instance input and checkpoints live in Turso or PostgreSQL; neither store contains an attachment model. Generated binaries in `crates/blkit-transpiler/src/project.rs` select role-specific core features. Existing `input_request` response posts also extract `Json<Value>`; both endpoints need optional multipart support while keeping their existing validation.

## Goals / Non-Goals

**Goals:** Preserve JSON-only request/response compatibility and `.bl` input contracts, require a usable attachment store for every runnable role, keep bytes outside both databases, enable durable worker access and keep local builds independent of cloud/remote stacks.

**Non-Goals:** Introduce a `.bl` `File` type, provide public file downloads, client-supplied storage URLs, presigned uploads, or automatic per-instance deletion/retention policy.

## Decisions

1. **Use Apache Arrow Rust `object_store`** for the common async read/write interface: its [documented implementations](https://docs.rs/object_store/latest/object_store/#available-objectstore-implementations) include local filesystem, AWS S3, GCS, and Azure Blob, and its [multipart upload API](https://docs.rs/object_store/latest/object_store/#multipart-upload) supports bounded streaming. Prefer it over implementing four SDK adapters or introducing a generic storage framework with many unrelated backends. Pin a compatible current release during implementation; enable `fs` for local and the relevant cloud provider features only in targets that need them. Credentials and endpoints come from provider-specific builder settings/environment, never from client requests.

2. **Use the same multipart pattern on both existing POST routes.** `Content-Type: multipart/form-data` has exactly one `input` JSON part on process starts or one `response` JSON part on input-request replies, plus repeated `files` parts carrying bytes, filename and optional media type. Reject duplicate/missing JSON parts, unsupported fields, empty/nameless files, and invalid JSON. Both JSON-only calls retain their current handler semantics; reply JSON still receives persisted-schema validation and conflict checks before committing. A single optional multipart decoder can serve both routes without a second upload endpoint. Use streaming multipart/body reads and bounded object writes (including local FS) rather than collecting files into memory. Explicit server defaults: at most 10 files, 25 MiB each and 100 MiB combined; return 413 when exceeded and 400 for invalid parts. Document limits; do not expose a new configuration surface unless real use demands one. The existing axum body-size default must be overridden for the multipart route while enforcing these bounds during streaming.

3. **Separate attachment metadata from typed JSON.** Add an `instance_attachments` table with instance ID (foreign key), nullable request ID, ordinal, generated object key, sanitized/display-only original filename, media type, and byte length. A start attachment has no request ID; a reply attachment references `(instance_id, request_id)` in `input_requests`; retain rows after that request is consumed. Use a uniqueness constraint for `(instance_id, scope, ordinal)` that treats all start files as one scope (ordinary NULL uniqueness alone is insufficient). Keep ordering stable and use server-generated non-guessable keys under an application-owned prefix; never join untrusted filenames to filesystem paths or log file contents. Keep a shared attachment-store handle available to API and worker roles; expose a Rust accessor to list metadata and open/read an attachment by instance ID, optional request ID and ordinal for worker-side Rust consumers, with no HTTP download route or `.bl` type/graph changes. Instance snapshots may expose safe filename/media type/size metadata to authorized clients but not object keys or bytes. Retain files for the same lifetime as persisted instances; no implicit deletion on cancellation.

4. **Accept only fully uploaded starts or replies.** Perform existing process/JSON or input-response validation before upload where possible; for remote starts retain the existing live-worker test and deferred typed start validation. Upload each object, then insert the new instance and its attachments in one database transaction, or conditionally accept the outstanding reply and insert its attachments in one transaction, preserving the current cancellation/deadline/duplicate-answer serialization and notification path. No DB transaction or connection is held across object uploads. Only a committed transaction yields 202; on validation, upload, conflict, or commit errors clean up uploaded objects best-effort. Crash between upload and commit may leave unreachable objects, not dangling committed references: document a safe manual orphan-audit procedure and private bucket/directory lifecycle requirements rather than inventing a distributed cleanup service. Do not delete an object on an uncertain DB commit outcome until checking its preassigned instance/request association. Tests must cover partial upload, commit failure, competing reply/cancel, retries and restart.

5. **Require storage at startup, without adding build targets.** A local binary defaults to `fs` with a persistent attachment directory alongside the selected database path; `BLKIT_ATTACHMENT_ROOT` may override that location. It checks directory creation/writability before serving. Every remote API and worker binary must select `BLKIT_ATTACHMENT_BACKEND=s3|gcs|azure` and configure the corresponding bucket/container, endpoint (where applicable), and provider credentials supported by its object-store builder; do not start without this configuration or if initialization fails, even for JSON-only traffic. Use the same logical store/prefix on API and workers, with read access for workers and write/read/delete access for API roles. Disallow `fs` in remote mode. Check configuration at startup and report runtime storage outages as errors; no skipped storage dependency or JSON-only fallback. Feature-gate cloud and local support to preserve generated target dependency boundaries. Dev-harness binaries follow the same rules.

## Risks / Trade-offs

- **Object write and database commit are not atomic** → Never acknowledge uncommitted work; best-effort compensation, a private orphan-audit/runbook, and no unsafe deletion on ambiguous commits.
- **Object-storage outage or missing object after admission** → Surface a worker execution error under existing retry policy; keep metadata intact for recovery rather than silently omitting the file.
- **Untrusted uploads consume disk/bandwidth or expose private contents** → Stream within count/size limits, use generated keys and private storage, and require existing operator-managed authenticated TLS ingress; do not log bytes or issue public object URLs.
- **Startup depends on a working configured store** → Fail early on absent/invalid settings and local directory problems; report cloud I/O failures explicitly. Operators must provision a shared cloud bucket/container before launching distributed roles.
- **Attachment files remain after terminal state** → Retention and deletion track existing instance retention policies; operator must manage backups, capacity and orphan audits until a dedicated deletion policy exists.

## Deployment

1. Create the `instance_attachments` schema as part of local/PostgreSQL store initialization; no migration of released installations is needed.
2. For a single node, place the database and default attachment directory on persistent storage, or configure another writable root. For distributed roles, provision a private shared cloud bucket/container and configure its backend and credentials on every API and worker before starting them. API needs write/read/delete and worker needs read access.
3. Document file backup/retention with the database: restoring attachment metadata without its objects leaves references unusable. JSON-only HTTP clients need no request changes.
